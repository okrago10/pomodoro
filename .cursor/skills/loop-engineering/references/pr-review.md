# 自動レビュー（Claude Code が PR に投稿する形式）

このリポジトリでは PR を open にしたあと、次のような **issue comment** が付く。

- `## コードレビュー結果`（`### [Major]` / `### [Minor]`）
- `## セキュリティレビュー結果`（指摘なし、または指摘あり）

投稿者 login はリポジトリオーナーでも、本文末尾に `_Generated by [Claude Code]` が付くことがある。**形式で判定する。**

## ループでの扱い

1 実行は「issue 選定 → PR」で終わらない。**最新の自動レビューの Major に対応するまで**（または指摘なしになるまで）同じ PR を扱う。

優先順位（ゲート通過後）:

1. オープン PR に、head コミットより新しい `[Major]` / `[Minor]` がある → **その PR を直す。新しいバックログ issue には着手しない**
2. オープン PR がレビュー待ち（まだ `## コードレビュー結果` が無い）→ **新しい issue に着手しない。** 同じ実行で数分待って再取得してよい。来なければ次のオートメーションに引き継ぐ
3. オープン PR の最新レビューが指摘なし、または指摘より後の commit がある → その PR はレビュー対応済み。次のバックログ issue へ進んでよい（未マージのまま次 issue に進むかは、同時 PR が増えすぎないよう **未マージの実装 PR が残っている間は次 issue に進まない**）

## 待ち方

PR 作成直後、最大おおよそ 10 分、1〜2 分おきに comments を取る。

```bash
gh api repos/<owner>/<repo>/issues/<n>/comments
```

`## コードレビュー結果` または `## セキュリティレビュー結果` が付いたら対応に入る。セキュリティが「指摘なし」だけでコードレビューに Major があるなら、コード側を直す。

## 直し方

- `[Major]` は必ず直す。直さないなら §2 のユーザー判断として着手せず報告する（レビュー内容が方針と衝突するときだけ）
- `[Minor]` も直す。仕様の解釈が割れるときだけ報告
- 同じブランチに commit / push し、既存 PR を更新する。新しい PR は作らない
- 対応内容を PR のコメントで返す（API が 403 なら PR 本文の末尾に「レビュー対応」を追記する）
- push したあと、フォローアップのレビューが来るまで同じ待ちを **最大もう 1 ラウンド** する。2 ラウンド直しても Major が残るなら技術リトライ扱い（§5）し、だめなら報告

## 未対応の判定

最新の対象コメントの `created_at` が、PR head commit の committer date より後で、かつ `### [Major]` または `### [Minor]` がある。

```bash
python3 .cursor/skills/loop-engineering/scripts/unaddressed_reviews.py
```

GitHub が取れないときは exit 4。**進行しない（フェイルクローズ）。**

## 終了

そのループの実装 PR について:

- 最新レビューが指摘なし、または指摘を直した commit がレビューより新しい
- そのうえで PR は open のまま残して実行終了（マージはユーザー）
