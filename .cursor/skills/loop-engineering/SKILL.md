# ループエンジニアリング（1実行 = 1 issue → PR）

このスキルを **1回実行したら、着手する issue の選定から PR 作成まで** を行う。複数 issue を実装しない。マージ待ちで止まらない（マージ後のバックログ更新は、次の実行の冒頭で行う）。

正となる進捗: GitHub issue **#13**。運用上のチェックリスト: リポジトリの `BACKLOG.md`（#13 を PATCH できない場合の正）。

## 0. ゲート（着手前に必ず）

順番に判定する。該当したら **実装に入らず** 終了する。

### 0.1 停止フラグ

次のいずれかがあれば作業しない。ユーザーへの再報告だけ行う。

- オープンな GitHub issue のタイトルが `[loop-halt]` で始まる
- ファイル `.cursor/loop/HALT` が default branch に存在する

報告文の型: 「オートメーションは停止中。`[loop-halt]` を close し、HALT ファイルを消すまでループしないでください。Cursor の Automation も無効化してください。」

### 0.2 未回答レポートの回数

オープンな `[loop-report]` issue を数える（タイトル接頭辞で検索）。

| オープン数 | この実行 |
| --- | --- |
| 0 | 通常どおり進む |
| 1 | **2回目まで許容。** ユーザー判断待ちなら実装しない。技術失敗の再実行なら、同じ issue をもう一度だけ試みる |
| 2 以上 | **3回目。** 実装しない。§7 でオートメーションを止める |

「ユーザーが報告に気づかず次のオートメーションが走った」状態は、未 close の `[loop-report]` が残っていることで検出する。

### 0.3 マージ済み PR のバックログ同期

実装の前に行う（これは issue 実装とは別の事務で、同じ実行内でやってよい）。

1. `gh pr list --state merged --limit 30` と `BACKLOG.md` を照合する
2. マージ済みで `Closes #N` / `Fixes #N` があるのにチェックが付いていない項目を `[x]` にする
3. 可能なら GitHub の #13 本文も同様に更新する。PATCH が 403 なら `BACKLOG.md` だけを正とし、同期が必要ならこの実行の PR に含める
4. 対象 issue を close できるなら close する。できないならユーザー報告に「#N を close してください」と書く

## 1. issue 選定

`BACKLOG.md` の **未完了の先頭** を次の着手にする。

スキップしてよいもの:

- 明示的にキャンセル（#2 の Expo 初期構築など）
- 進捗管理 issue 自体（#10 / #13）
- `[loop-report]` / `[loop-halt]` / 権限確認用の #1

選定したら issue 本文を読む。**その issue のエピック・タスク・受け入れ条件だけ** がスコープ。先の issue を先取りしない。

着手不能（依存未完了、本文が空、キャンセルと現行方針が矛盾）なら、ユーザー判断が要るか技術リトライかを §5 / §6 で分岐する。

## 2. ユーザー判断が必要か（必要なら着手しない）

基本はエージェントが決めて進めてよい。次に当てはまるときだけ **着手せず報告**（§6）する。

判断が必要な例:

- プロダクトの挙動が二択以上あり、受け入れ条件では決められない
- サイクル時間・ボタン構成・技術スタックなど、既存の確定方針を覆す必要がある
- 秘密情報、有料プラン、外部アカウント、GitHub Pages 以外のホスティング
- セキュリティ・法務・個人情報
- バックログの削除・優先度の入れ替え
- 実装すると既存の確定（Vite + GitHub Pages、サーバなし、最小ボタン）と衝突する

判断しなくてよい例（進めてよい）:

- ライブラリのパッチバージョン、ファイル分割、コンポーネントの見た目の細部（迷わせない範囲）
- テストの書き方、リトライ可能な CI 失敗
- #9 のチャート **または** カレンダー（どちらか一方を選ぶ）

## 3. 実装

- default branch から `feature/<short-name>-51db` を切る（既存のブランチ命名に合わせる）
- スコープ外のリファクタや依存追加をしない
- 確定スタック: React + TypeScript + Vite + Tailwind CSS v4 + HeroUI React v3 + Effect。デプロイは GitHub Pages。サーバ・Expo・HeroUI Native は使わない
- サイクルの正は issue #3（未実装なら #3 の本文）: `作業25 → 短い休憩5 → 作業25 → 長い休憩15`、終了で自動遷移
- 一時的な失敗は §5 のとおり最大 2 回リトライ

## 4. 動作確認と PR

PR を出す **前** に、変更が画面に出るなら証拠を撮る。

1. アプリを起動する（Vite なら dev server）
2. iPhone 16 幅（390×844 程度）を意識する
3. スクリーンショット、または短い操作動画を撮る（Computer Use / RecordScreen など、環境にある手段）
4. 画像・動画を成果物として残し、PR 本文に埋め込む（`<img>` / `<video>`。Cloud Agent なら成果物の絶対パスでよい）
5. UI が無い変更（このスキル追加など）は、その旨を本文に書き、代わりに実行した検証コマンドと出力を載せる。**画面があるのに証拠が無い PR は出さない**

PR 本文に必ず含める:

- 対象 issue とエピック
- やったこと / やらなかったこと
- 受け入れ条件との対応
- 動作確認のスクショまたは動画
- `Closes #N`（その issue を完了にするとき）
- `BACKLOG.md` の該当行を `[x]` にしたこと

PR 作成後、**この実行は終了**する。マージはユーザーまたは既存の automerge に任せる。

## 5. 技術リトライ（最大 2 回）

同じ実行の中で、次に進めない障害が起きたら **同じ手順を最大 2 回まで** やり直す（初回 + リトライ 2 = 計 3 試行）。

リトライしてよい: ネットワーク、`npm i`、push、フレークなテスト、dev server の起動失敗。

リトライしてはいけない: §2 のユーザー判断、スコープが壊れている、テストが仕様として落ちる。

2 回リトライしても次に進めない → 実装を打ち切り、§6 で報告する。部分的な危険なコミットは push しない。説明可能な途中状態だけ残してよい。

## 6. ユーザーへの報告（着手しない / 打ち切り）

実装しないと決めたら:

1. GitHub に issue を作る。タイトルは  
   `[loop-report] <短い理由> (<何回目/2>)`  
   例: `[loop-report] #11 の受け入れ条件が矛盾 (1/2)`
2. 本文に: 止まった理由、試したこと、ユーザーに決めてほしいこと、次にループを回してよいか
3. 実行の最終メッセージでも同じ内容を報告する
4. **コード変更を始めない**（すでにブランチがあるなら破棄または push しない）

何回目かは、既存のオープン `[loop-report]` 数 + 1。これが 3 以上になるなら issue を増やす前に §7 へ。

## 7. 3 回目: オートメーションを一時停止

オープン `[loop-report]` が既に 2 件ある状態で、さらにユーザー未回答のまま実行されたら:

1. `[loop-halt] 未回答レポートが3回目のため停止` という issue を作る
2. 可能なら `.cursor/loop/HALT` を追加する PR を出す（タイトルに `STOP AUTOMATION` を含める）。中身は停止理由と、解除手順（halt issue を close、HALT を削除、report issue を close、Cursor Automation を再度 enable）
3. Cursor の Automation を API で disable できない場合は、最終報告で **ダッシュボード上で Automation をオフにする** よう明記する（`get-automation` は参照のみ）
4. 以降のループ実行は §0.1 で即終了する

目的: 報告に気づかないまま作業が進み続けないようにする。

## 8. 終了条件（このスキルの成功）

次のいずれかで終了する。

- PR を作成し、スクショ/動画（または UI 無しの検証ログ）を付けた
- ユーザー判断待ちで `[loop-report]` を作り、実装していない
- リトライ 2 回後も進めず報告した
- `[loop-halt]` で止めた
- 未完了バックログが無い（その旨報告して終了）

## やってはいけないこと

- 1 実行で 2 つ以上のバックログ issue を実装する
- 判断待ちなのに「仮決め」で実装を進める
- サーバを建てる、Expo に戻す、分数設定画面やスキップボタンを勝手に足す
- halt 中に「少しだけ」実装する
- 動作確認証拠なしで UI 変更の PR を出す
